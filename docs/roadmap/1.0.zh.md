# 1.0 远景：统一个人助手的长期形态

状态：**远景计划（NOT-STARTED）**。本文只记录已同意的长期方向，不表示 1.0 已排期或已实现，也不改变 0.0.1—0.0.4 的已批准顺序与范围。代码、测试与验收记录决定实际状态；本文不是发布承诺。

## 1. 长期用户目标

Nisse 是用户唯一的个人助手入口：在桌宠、耳机或 Pad 上交代工作，由 Main Bot 协调多个执行 Bot，云端持续执行，Hindsight 保存有权限边界的长期记忆，结果以“一分钟简报 + 完整成果”分层交付。

目标流程：

1. 理解或澄清目标、对象与范围。
2. 创建可追踪任务，必要时请求批准。
3. 分派给专门的执行 Bot 并行或串行处理。
4. 用户断开语音后，已提交任务继续执行；完成后通知。
5. 耳机播放摘要，Pad/主窗口查看完整成果与证据。
6. 用户可继续追问、修改、停止或撤销。

示例（合成数据）：“让研究 Bot 查竞品，让分析 Bot 整理价格，完成后给我一分钟汇报。”

## 3. 组件职责

- **DSH**：唯一 Agent Runtime；0.0.x 期间保持锁定版本，1.0 的升级需单独评估兼容性。
- **Pipecat**：当前语音链路；1.0 可增加系统本地 TTS，但不改变“ASR/TTS 是语音管线”的事实。
- **Hindsight**：个人长期记忆系统；1.0 的记忆统一以它为唯一写入责任方，其他 Bot 通过适配器读取。
- **Main Bot**：统一入口与协调者，复用 DS-Bot 的团队协作能力，不另建竞争调度中心。
- **执行 Bot**：承担研究、分析、本地操作等专门任务；各自有明确权限边界与结果格式。
- **桌面桌宠**：本地交互界面与本地权限执行端；不因云端在线而自动授予文件或系统权限。
- **云服务**：持续执行、任务状态、通知、跨端同步；公网暴露必须有独立鉴权与安全设计。
- **耳机/Pad**：耳机负责采音、交代、确认与听简报；Pad 负责进度、审批、修改与阅读成果。

## 4. 任务与状态模型

- 每个任务有唯一身份、创建者、目标、范围、所属 Bot、审批记录、结果与证据。
- 语音会话与任务生命周期分离：断开耳机、关闭前端或切换设备不取消已提交任务。
- 请求去重、事件恢复、审批撤销与取消范围必须明确；旧事件不能操作新任务。
- 任务可以等待、重试、取消或明确失败；不允许“看起来成功”的假状态。
- 多 Bot 进度汇总时，用户看到统一进度与阻塞，而不是多个互相覆盖的状态源。

## 5. 记忆统一

- Hindsight 仍是个人长期记忆的唯一主存储；DS-Bot 记忆能力只作为受控读写接口。
- 保留个人、Bot、群组、团队与任务记录的权限边界；统一记忆不等于所有 Bot 共享全部私人内容。
- 迁移保留来源、时间、权限与可回滚信息；重复迁移幂等，失败不丢原数据。
- 支持查看、纠正、删除，并在跨 Session、跨重启与跨端后保持可验证一致性。
- 不允许“双写后以后再解决”制造两套冲突的事实来源。

## 6. 语音、TTS 与陪伴体验

- 保留云端 ASR/TTS 作为默认链路；系统本地 TTS 作为可选，必须实测中文效果、首响、内存、资源与许可。
- 本地 TTS 不等于整个助手离线；网络不可用时明确说明受限能力。
- 语音优先简短播报，完整结果在 Pad/主窗口查看；不重复播报、不抢话。
- “停止播放”与“停止任务”分开；打断只影响当前语音输出。
- 动作、触碰、视线与过渡参考成熟陪伴产品，但独立核实代码、素材许可与可维护性；不整体换皮替代交互优化。

## 7. 云端持续执行

- 云端 DSH/DS-Bot 承载长任务、定时任务与团队协作；持久化任务状态与恢复点。
- 断网、断语音或关闭前端后，已提交任务继续；重连时按任务身份恢复，不重复执行。
- 本地 Mac 操作通过有权限的在线执行端完成；Mac 离线时，本地任务等待或明确失败。
- 审批路由到当前可用的用户界面；无接收者时 fail-closed 并给出明确恢复入口。
- 成本、并发、超时与预算对用户可见；超过预算按策略暂停或终止。
- 公网连接独立鉴权，不直接暴露现有回环接口；不默认上传全部本地文件、凭据或浏览器登录态。

## 8. 耳机＋Pad

- 同一用户、同一 Nisse 身份、同一任务与记忆语义跨端一致。
- 明确哪个设备收音、哪个设备播报，避免回声与重复响应；设备切换有确定行为。
- 耳机断连、网络变化与重连有明确状态；普通蓝牙耳机仍需手机/Pad 等联网主机。
- 前台网页可先验证体验，但不假设锁屏/后台音频能力已具备；必要时使用原生客户端。
- 不承诺耳机本身独立运行 Agent，也不把 Mac 桌宠窗口形态原样搬到 Pad。

## 9. 双交付

1. **完整 App**：携带隔离 Runtime，开箱可用，适合个人直接安装。
2. **原版 DSH 插件＋受管理的桌宠伴随程序**：接入用户已有 DSH，不污染已有 DSH HOME，不额外启动重复主助手。

两种交付共享协议与行为，但分别验证安装、升级、退出、权限、数据归属与更新责任。插件模式不要求用户复制同一套配置，也不得把原版 DSH 变成第二个主 Agent。

## 10. 依赖与验收

进入 1.0 评估前必须满足：

- 0.0.1—0.0.4 分别完成各自验收，历史证据保留且绑定源码/产物身份。
- Main Bot 与执行 Bot 的请求去重、审批撤销、任务恢复在真实故障下验证。
- Hindsight 统一迁移可回滚、幂等，并有跨 Session/重启/跨端验证。
- 云端公网端有独立鉴权与最小权限设计；无凭据不能控制或读取敏感状态。
- 耳机＋Pad 原型完成真实设备与真实网络条件测试，不把 mock 当验收。
- 所有新增能力保留现有桌宠、语音、人格与用户数据；删除旧链路前证明无引用。

验收记录必须区分：mock/fixture、真实 Provider、真实声学、真实设备、人工体验；IMPLEMENTED 不等于 VERIFIED。

## 11. 风险与未决定事项

- **未决定**：云端部署形态（自托管/托管）、任务身份与多端同步协议、耳机/Pad 的客户端形态。
- **未决定**：哪些任务允许后台自动继续，哪些必须每次审批；审批预算与超时策略。
- **未决定**：本地 TTS 的选型与许可；多 Bot 记忆共享的默认边界。
- **风险**：团队协作与个人助手身份冲突；跨端状态不一致；公网暴露扩大攻击面；长期记忆误共享；成本不可控。
- **风险**：过早实现 1.0 会挤占 0.0.1 稳定化与真机验收，本文件明确禁止提前开发。
