# DashScope TTS 300 秒超时 — 已知问题跟踪

## 状态
**OPEN / 根因未确认 / 未修复。** 不得写成已修复或 PASS。

## 历史证据
- 长矩阵测试末尾出现：
  `DashScope TTS error: CLIENT_ERROR request timeout after 300 seconds`
- 当时客户端 `status=error`，语音输出中断。
- 后续 50 轮（约 10 分钟）受控矩阵未复现同一错误。

## 已实现的缓解
- TTS provider error/timeout 路径：
  - 解除 `run_tts` 的等待阻塞；
  - 关闭旧 websocket；
  - 交给 Pipecat base reconnect（指数退避）；
  - 下一轮合成等待 `socket_ready` 后再发送；
  - 发送失败使用 `send_with_retry`。
- 注入 provider error 验证：
  - 第一轮音频丢失（预期）；
  - reconnect 成功；
  - 下一回合音频正常播放；
  - 客户端状态定向修复后恢复为 `connected`，历史错误保留。

## 未解决
- 原始 300 秒超时的触发条件、服务端/网络原因未确认；
- 未验证真实 300 秒边界与恢复；
- 受影响回合会丢失音频；
- 是否需要主动在 300 秒前重建 TTS 连接，暂无证据支持，未实施。

## 影响评估
- 当前 MVP 命令式打断门控不受影响；
- 长会话 TTS 可能中断一次，用户需要下一回合恢复；
- 发布前需决定：接受风险并记录，或继续专项复现。

## 后续建议
1. 单列长会话 TTS soak：持续合成 >300 秒/连续多回合，记录 websocket 生命周期与错误；
2. 检查 DashScope 服务端 300s 限制文档/错误码；
3. 若确认固定期限，再评估主动重建连接；
4. 任何修复后只做定向回归，不重跑 G2/P1 全矩阵。
